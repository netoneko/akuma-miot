# Key management

Written 2026-09-23, prompted by the AWS-deploy security pass
(`docs/MESH_AUTH.md`): once the account's own key started backing transport
(mTLS) and not just chain authorization, "which key" stopped being a dev
convenience question and became the whole security model. This doc says
what's actually at stake, what the fleet already does right, the one real
footgun, and the procedure for a fresh genesis — including the one an AWS
node joins.

## The model, in one line

An account *is* an ed25519 public key (`miot_keys::Identity` wraps
`sp_core::ed25519::Pair`; `AccountId32::new(pair.public().0)` — the account,
not a hash of it). There is no separate identity layer to compromise
independently of the key: whoever holds the private key *is* that account,
everywhere, for everything below.

## What one key now backs

Before this session, an account's key authorized exactly one thing:
`/submit`'s `UncheckedExtrinsic` signature (`CheckNonce` et al. — chain
writes). After today it backs three, and all three collapse to the same
question — *does the caller hold this account's private key* — so a
guessable key doesn't just let someone forge a chain write, it lets them
read everything and impersonate the account at the transport layer too:

1. **`/submit`** — unchanged, the extrinsic's own signature.
2. **Every client-facing read and all mesh-internal traffic** — the
   `x-miot-signer`/`x-miot-sig` header envelope, checked against
   `Node::is_trusted_signer` (`docs/MESH_AUTH.md`).
3. **The TLS connection itself, both directions** — `crates/kot/src/tls.rs`
   pins a self-signed cert's embedded pubkey against the same trusted set.
   Mutual: a `kot` client needs a cert the node trusts, and the node's own
   cert needs to be one the client trusts.

One compromised (or merely guessable) seed now undoes all three at once.

## The dev-seed footgun

`common::parse_seed` accepts a small integer as a seed — `Identity::from_seed(&[n; 32])`
— and says so itself: *"fine for a throwaway local litter, never for a real
deployment."* The footgun isn't that this exists (it's a genuinely useful
dev convenience — deterministic, greppable, zero setup for a laptop-only
chain); it's that `kot`'s own CLI defaults lean on it:

| flag | env | default |
|---|---|---|
| `--root` | `MIOT_ROOT_PUBKEY` | `"1"` |
| `--leader` | `MIOT_LEADER` | `"2"` |
| `--members` | `MIOT_MEMBERS` | `"1,2,3,4,5"` |
| `--roster` | `MIOT_ROSTER` | `DEV_ROSTER = "root=1,simlead=2,sima=3,simb=4,simc=5"` |

(`crates/kot/src/main.rs`.) Miss overriding *any one* of these four and that
invocation silently rejoins the dev genesis — an attacker doesn't need to
steal anything, `Identity::from_seed(&[1; 32])` is one line anyone can run,
and it's now printed in this very doc.

**Checked, not assumed:** the actually-deployed 5-agent fleet does not have
this problem. `overlays/deploy/mesh.env` — "Genesis for the 5-agent mesh —
generated by `deploy.py ids`" — holds a real `ssh-ed25519` root key and full
64-hex pubkeys for leader/members/roster, none of them dev seeds. The risk
here is in ad hoc or manual invocations (a local test habit, or a shell
that hasn't sourced `mesh.env`) landing somewhere that matters, not in the
fleet's own genesis as it stands today.

## The genesis procedure that already exists

`overlays/deploy/deploy.py ids` (and `deploy.sh ids`, kept byte-for-byte
equivalent — `CLAUDE.md`) is the real, working genesis-generation
procedure. What it actually does, in order:

1. **For each live agent** (`LIVE` in `deploy.py`) — ships the `kot`
   binary, then runs, over SSH, `kot --seed-file /root/kot/id_ed25519.seed
   id --comment <name>` on that host (`account_of`, `deploy.py:276`).
   `kot id` (`common::load_or_create_identity`) creates the identity only
   if the seed file doesn't already exist — real `getrandom` entropy,
   written 0600 — and is a no-op on a host that already has one, so
   re-running `ids` never silently mints a new key for an agent that's
   already provisioned. It prints the account's hex on the first line,
   which is what the script captures.
2. **For not-yet-live agents** (the two Firecracker/akuma guests not yet
   booted) — the same `kot ... id` invocation runs *locally* first
   (`_kot_id_local`, `deploy.py:285`), staging the identity to be moved
   into the guest's rootfs once it exists.
3. **Root's own identity** — generated/loaded the same way, but only ever
   locally, at the operator's own `~/.akuma/miot/id_ed25519.seed`
   (`common::root_identity_path`). It is never shipped to any node; only
   its public `ssh-ed25519` line (`~/.akuma/miot/id_ed25519.pub`) is.
4. **Assembly**: `members` = root + every agent's account; `roster` =
   `name=pub:<hex>` for each (public keys only — no seed ever enters this
   file); `leader` = the first agent in `LIVE`, by convention, not a
   deliberate choice per run.
5. **`overlays/deploy/mesh.env`** gets written with `MIOT_ROOT_PUBKEY`,
   `MIOT_LEADER`, `MIOT_MEMBERS`, `MIOT_ROSTER` and the comment "Public
   keys only. Every node must agree on all of this: it is genesis." Safe
   to keep in the repo/share — it holds no secret material, by
   construction.
6. Later, `env_for(name)` (`deploy.py:351`) reads `mesh.env` back and folds
   it into each agent's own env file, alongside *that* agent's own
   `MIOT_SEED_FILE` path — never another agent's seed.

## What adding an AWS node changes

The full step-by-step procedure is `docs/runbooks/deploy-aws-node.md`. This
section is the summary.

An AWS node joining the mesh (as a full peer, not just a client-facing
gateway — the topology this session settled on) is a new member of a new
genesis, not an incremental join (`CLAUDE.md`: *"Mesh membership is
static... changing either is a coordinated restart, not an operation"*).
Concretely:

1. Add the AWS host wherever `deploy.py`/`deploy.sh` enumerate live agents
   (`LIVE`, and `route()`'s per-host addressing) so it goes through the
   exact same `ids` path as every existing agent — no special-casing a
   pubkey by hand.
2. Re-run `ids`. This regenerates `mesh.env` with the new member folded
   into `MIOT_MEMBERS`/`MIOT_ROSTER` (and possibly a different
   `MIOT_LEADER`, since that's just "whoever's first in `LIVE`") — a new
   genesis, which is exactly why this is being done as a coordinated
   restart rather than live.
3. Every node needs the regenerated `mesh.env`, the new binary (mTLS
   support, `docs/MESH_AUTH.md`), and `https://` peer URLs, all at the same
   restart — the same hard-cutover the mTLS work already requires, not a
   second one.
4. `overlays/deploy/*`, `docs/TOPOLOGY.md`, and
   `docs/runbooks/run-the-mesh.md` still assume the old scheme/inventory —
   left for this migration pass rather than hand-edited mid-conversation
   (`docs/MESH_AUTH.md`'s mTLS section explains why).

## Rules for next time

- Never let `--root`/`--leader`/`--members`/`--roster` fall through to
  `kot`'s own defaults for anything beyond a disposable local chain —
  source `mesh.env` (or its post-migration, AWS-inclusive successor)
  explicitly, every time.
- Root's seed leaves the operator's own machine for no reason, ever —
  `mesh.env` and every other genesis artifact hold only its public half.
- A fresh genesis is the natural moment to mint fresh keys for any
  newly-provisioned host; it is not a reason to touch the seed of a host
  that already has one — `kot id`'s own idempotency already protects that,
  don't work around it.
